# 第 14 章 诊断库

程序出错是常态：文件找不到、网络超时、输入非法、指针空了……如何及时发现问题、定位问题、记录问题，是诊断库的职责。本章覆盖：

- 14.1 断言、`errno` 与系统错误：`assert`、`errno`、`std::error_code` / `std::error_condition`；
- 14.2 标准异常层次与异常安全：`std::exception` 派生体系、`what()` 契约、`noexcept`；
- 14.3 `std::stacktrace`：程序化调用栈捕获（C++23）。

> **工具约定**：示例以 C++20 为基线；`std::stacktrace` 是 C++23 特性，链接时可能需要额外库（GCC/Clang 通常需 `-lstdc++exp`，MSVC 需 `/std:c++23` 且标准库支持），使用前请确认编译器和标准库版本。代码片段可用 `cxxsh` 单文件验证，放入真实项目时请套用第 7.7 节的 CMake + vcpkg 工程模板。

## 14.1 断言、`errno` 与系统错误

### 14.1.1 `assert`：开发期的“自我检查”

`assert`（`<cassert>`）是最简单的诊断手段。它接收一个布尔条件，如果条件为假，程序会立即终止并打印错误信息（包含文件名、行号、表达式）：

```cpp
// assert_basic.cpp
#include <cassert>
#include <iostream>

int main() {
    int age = 25;
    assert(age >= 0 && age <= 150);   // 条件为真，什么都不发生，程序继续

    std::cout << "年龄合法：" << age << '\n';

    // assert(-1);   // 取消注释看看：程序会中止，并打印断言失败信息
}
```

`assert` 的核心设计理念是：**捕捉“程序员应该保证永远不会发生”的情况**。比如“指针不应为空”“下标不应越界”“函数入口参数应满足前置条件”。它不是用来处理“用户输入了错误数据”这类运行期可预见错误的，那些应该用异常或错误码。

`assert` 还有一个重要特性：在定义了 `NDEBUG` 宏时（通常是 release 构建），所有 `assert` 都会被编译器**彻底忽略**，不产生任何代码、不产生任何运行期开销。所以 `assert` 适合在 debug/测试阶段大量使用，发布版本自动零开销。

```bash
# 普通编译（debug）：assert 起作用
g++ -std=c++20 assert_basic.cpp -o assert_basic

# 定义 NDEBUG（release）：assert 被移除
g++ -std=c++20 -DNDEBUG assert_basic.cpp -o assert_basic_release
```

**避坑**：`assert` 里的表达式不能有副作用。比如 `assert(++count > 0)` 在 release 里会被整个移除，导致 `count` 永远不会被递增，引出难以排查的 bug。`assert` 里只写纯检查条件，不修改任何状态。

### 14.1.2 `errno`：C 语言遗留的错误码

`<cerrno>` 定义了 `errno`，一个全局（或线程局部）整数变量，许多 C 标准库函数在出错时会设置它。常见的错误码宏包括：

- `EINVAL`：无效参数；
- `ENOENT`：文件或目录不存在；
- `EACCES`：权限不足；
- `EIO`：I/O 错误；
- `ERANGE`：结果超出范围。

```cpp
// errno_basic.cpp
#include <iostream>
#include <cerrno>
#include <cmath>
#include <cstring>

int main() {
    errno = 0;                    // 调用前先清零
    double result = std::sqrt(-1.0);  // 负数开方，出错

    if (errno != 0) {
        std::cerr << "sqrt 出错，errno = " << errno << '\n';
        // strerror 把错误码转成可读字符串
        std::cerr << "错误信息：" << std::strerror(errno) << '\n';
    }
}
```

可能的输出：

```
sqrt 出错，errno = 33
错误信息：数值结果超出范围
```

`errno` 的缺点很明显：
1. 它是全局/线程局部状态，不是函数返回值的一部分，容易遗漏检查；
2. 你必须记得在调用前清零，调用后再检查，否则可能读到上一次调用留下的陈旧错误码；
3. 它只能传递一个整数错误码，无法携带丰富的上下文信息。

现代 C++ 代码中，**优先使用 `std::error_code` 或异常**，`errno` 主要用于和 C 标准库或操作系统 API 互操作时。

### 14.1.3 `std::error_code` / `std::error_condition`：类型安全的系统错误

C++11 引入了 `<system_error>` 里的 `std::error_code`，它是 `errno` 的类型安全升级版：一个 `error_code` 对象包含一个整数错误值和一个错误类别（category），能更精确地表示“哪里出了什么错”。

```cpp
// error_code_basic.cpp
#include <iostream>
#include <system_error>
#include <fstream>

int main() {
    std::ifstream in("不存在的文件.txt");
    if (!in) {
        // 把流的错误状态转成 error_code
        std::error_code ec(in.rdstate(), std::iostream_category());
        std::cerr << "错误码值：" << ec.value() << '\n';
        std::cerr << "错误类别：" << ec.category().name() << '\n';
        std::cerr << "错误信息：" << ec.message() << '\n';
    }
}
```

可能的输出：

```
错误码值：2
错误类别：iostream
错误信息：流错误
```

`std::error_code` 的关键成员：
- `value()`：返回具体的错误整数值；
- `category()`：返回错误类别（如 `iostream_category`、`generic_category`、`system_category`）；
- `message()`：返回可读的错误信息字符串；
- `operator bool()`：`error_code` 为空（值为 0）时转换为 `false`，非空时为 `true`，可以直接用 `if (ec)` 判断是否出错。

`std::error_condition` 与 `error_code` 相似，但它的设计目标是**可移植的抽象错误条件**。同一个操作系统的不同错误码可能映射到同一个 `error_condition`，方便跨平台统一处理。

```cpp
// error_condition_basic.cpp
#include <iostream>
#include <system_error>

int main() {
    std::error_code ec(2, std::generic_category());   // 某个平台的错误码 2
    std::error_condition cond = ec.default_error_condition();  // 映射为抽象条件

    if (cond == std::errc::no_such_file_or_directory) {
        std::cout << "归纳为：文件或目录不存在\n";
    }
}
```

### 14.1.4 三种错误诊断方式怎么选

| 方式 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|
| `assert` | 程序员应该保证不会发生的条件（前置条件、内部不变式） | 简单，release 零开销 | 失败直接终止，不可恢复；不适合用户输入错误 |
| `errno` | 和 C 标准库/操作系统 API 互操作 | C 语言兼容 | 全局状态、易遗漏、无上下文、不类型安全 |
| `std::error_code` | 可预见的系统/IO 错误、禁止异常的环境 | 类型安全、可携带类别、可比较 | 需要显式检查返回值，容易漏检 |

选型口诀：**内部逻辑“绝不可能发生”用 `assert`；可预见的运行期错误用 `error_code` 或异常；和 C API 打交道时才碰 `errno`。**

## 14.2 标准异常层次与异常安全

### 14.2.1 异常的基本用法

C++ 异常使用 `throw` 抛出，`try / catch` 捕获。异常适合“异常情况”——不应该经常发生、发生后需要中断当前流程并向上层传播的错误。

```cpp
// exception_basic.cpp
#include <iostream>
#include <stdexcept>
#include <string>

double divide(double a, double b) {
    if (b == 0.0) {
        throw std::invalid_argument("除数不能为零");
    }
    return a / b;
}

int main() {
    try {
        double result = divide(10.0, 0.0);
        std::cout << "结果：" << result << '\n';
    } catch (const std::invalid_argument& e) {
        std::cerr << "捕获到参数错误：" << e.what() << '\n';
    } catch (const std::exception& e) {
        std::cerr << "捕获到标准异常：" << e.what() << '\n';
    }
}
```

输出：

```
捕获到参数错误：除数不能为零
```

关键点：
- `throw` 后面跟一个异常对象，控制流立即跳转到最近的匹配 `catch` 块；
- `catch` 按异常类型匹配，子类对象可以被父类引用捕获（所以建议捕获 `const std::exception&` 作为兜底）；
- `e.what()` 返回一个 C 风格字符串，描述错误信息。

### 14.2.2 标准异常层次

标准库定义了一组异常类，都继承自 `std::exception`，定义在 `<stdexcept>` 中：

```
std::exception
├── std::logic_error       // 程序逻辑错误，可通过检查代码避免
│   ├── std::invalid_argument   // 无效参数
│   ├── std::domain_error       // 域错误（如数学函数输入越界）
│   ├── std::length_error       // 长度错误（如 vector 超过最大尺寸）
│   └── std::out_of_range       // 下标越界
├── std::runtime_error     // 运行期错误，仅在运行期可检测
│   ├── std::overflow_error   // 数值溢出
│   ├── std::underflow_error  // 数值下溢
│   └── std::range_error      // 范围错误
├── std::bad_alloc         // 内存分配失败（new 抛出）
└── std::bad_cast          // dynamic_cast 失败
```

选型建议：
- 如果是“传了个不该传的参数” → `std::invalid_argument`；
- 如果是“索引越界” → `std::out_of_range`；
- 如果是“文件打不开/网络超时”等运行期环境问题 → `std::runtime_error`；
- 如果是“内存分配失败” → 通常不需要自己抛，`new` 失败会自动抛 `std::bad_alloc`。

自定义异常时，继承 `std::runtime_error` 或 `std::logic_error`，重写 `what()` 即可：

```cpp
class MyError : public std::runtime_error {
public:
    explicit MyError(const std::string& msg) : std::runtime_error(msg) {}
};
```

### 14.2.3 `noexcept`：承诺“不抛异常”

`noexcept` 是 C++11 引入的异常规范，表示函数承诺不抛异常。它有两种形式：

- `noexcept`：绝对不抛；
- `noexcept(false)`：可能抛（相当于不写，但显式表达意图）。

```cpp
// noexcept_basic.cpp
#include <iostream>

void safe() noexcept {
    // 承诺不抛异常
    std::cout << "安全函数\n";
}

void unsafe() {
    // 可能抛异常
    throw std::runtime_error("出错");
}

int main() {
    safe();          // OK
    // unsafe();    // 如果抛出，main 没有 catch，程序会调用 std::terminate
}
```

`noexcept` 的好处：
1. **编译器优化**：编译器知道该函数不抛异常，可以生成更精简的代码（不需要展开栈的清理逻辑）；
2. **移动语义**：如果移动构造函数标记为 `noexcept`，容器（如 `std::vector`）在扩容时会优先使用移动而不是复制，提升性能；
3. **文档意图**：告诉调用者“这个函数不会抛异常，你不需要 catch”。

**避坑**：如果一个标记了 `noexcept` 的函数实际上抛出了异常，程序会调用 `std::terminate()` 直接终止，不会触发任何 `catch`。所以 `noexcept` 是一种“承诺”，写上之后必须确保函数内部（包括调用的所有函数）真的不会抛异常。

```cpp
void bad() noexcept {
    throw std::runtime_error("我违反承诺了");  // 运行时调用 std::terminate，程序崩溃
}
```

### 14.2.4 异常安全等级

编写异常安全代码时，通常参考 Abrahams 异常安全等级，从弱到强：

1. **基本异常安全（Basic guarantee）**：异常发生后，程序没有泄漏，对象保持在“合法但未指定”的状态；
2. **强异常安全（Strong guarantee）**：异常发生后，程序状态回滚到调用前，就像操作从未发生过；
3. **不抛异常保证（No-throw guarantee）**：函数承诺绝不抛异常。

日常开发中，强异常安全是理想目标，但不是所有操作都能做到（比如同时修改多个对象时）。基本异常安全（不泄漏、不崩溃）是底线。

> **小结**：`assert` 用于开发期自我检查，release 零开销；`errno` 是 C 遗留，现代代码优先 `error_code`；`std::exception` 派生体系覆盖常见错误场景；`noexcept` 是不抛异常的承诺，能帮助编译器优化和容器移动优化，但违反承诺会导致 `std::terminate`。

## 14.3 `std::stacktrace`：程序化调用栈捕获

### 14.3.1 为什么需要调用栈

程序崩溃或报错时，光知道“哪里出错”往往不够，还需要知道“是怎么一步步运行到这里的”——也就是**调用栈（call stack）**。传统上，获取调用栈需要平台相关的 API（如 Windows 的 `CaptureStackBackTrace`、Linux 的 `backtrace`），代码不可移植。

C++23 引入了 `std::stacktrace`（`<stacktrace>`），提供跨平台、类型安全的调用栈捕获和遍历能力。

### 14.3.2 基本用法

```cpp
// stacktrace_basic.cpp
// 需要 C++23 编译器和标准库支持；GCC/Clang 通常需链接 -lstdc++exp
#include <iostream>
#include <stacktrace>

void level3() {
    auto st = std::stacktrace::current();
    std::cout << st << '\n';
}

void level2() {
    level3();
}

void level1() {
    level2();
}

int main() {
    level1();
}
```

可能的输出（不同平台格式不同）：

```
0# level3() at ./stacktrace_basic.cpp:8
1# level2() at ./stacktrace_basic.cpp:12
2# level1() at ./stacktrace_basic.cpp:15
3# main at ./stacktrace_basic.cpp:18
```

`std::stacktrace::current()` 捕获当前的调用栈，返回一个 `std::stacktrace` 对象，可以直接打印，也可以遍历其中的每个 `stacktrace_entry`：

```cpp
#include <iostream>
#include <stacktrace>

void foo() {
    auto st = std::stacktrace::current();
    for (const auto& frame : st) {
        std::cout << frame.source_file() << '(' << frame.source_line() << ") "
                  << frame.source_function() << '\n';
    }
}
```

`std::stacktrace_entry` 的常用成员：
- `source_file()`：源文件名；
- `source_line()`：源码行号；
- `source_function()`：函数名；
- `description()`：描述信息（实现定义）。

### 14.3.3 典型应用：增强崩溃报告与日志

`std::stacktrace` 最常用的场景是：在捕获异常或检测到错误时，把当前调用栈一并记录到日志或崩溃报告里，方便事后定位。

```cpp
// stacktrace_with_exception.cpp
// 需要 C++23
#include <iostream>
#include <stacktrace>
#include <stdexcept>

void deep_function() {
    throw std::runtime_error("深层函数出错");
}

void middle_function() {
    deep_function();
}

void top_function() {
    middle_function();
}

int main() {
    try {
        top_function();
    } catch (const std::exception& e) {
        std::cerr << "异常：" << e.what() << '\n';
        std::cerr << "调用栈：\n" << std::stacktrace::current() << '\n';
    }
}
```

可能的输出：

```
异常：深层函数出错
调用栈：
0# deep_function() at ./stacktrace_with_exception.cpp:8
1# middle_function() at ./stacktrace_with_exception.cpp:11
2# top_function() at ./stacktrace_with_exception.cpp:14
3# main at ./stacktrace_with_exception.cpp:19
```

### 14.3.4 使用注意事项

1. **编译器和标准库支持**：`std::stacktrace` 是 C++23 特性，GCC 需要较新版本并链接 `-lstdc++exp`，MSVC 在较新版本中支持；使用前务必确认工具链支持。
2. **性能开销**：捕获调用栈不是零成本的操作，不要在高频热点代码里频繁调用 `std::stacktrace::current()`；适合在错误路径、日志记录、崩溃处理中使用。
3. **符号化**：调用栈能否显示函数名和行号，取决于编译器是否生成了调试信息（如 `-g` 选项）以及是否保留了符号表。Release 构建若去掉了符号，输出可能只有地址，没有可读的函数名。

> **小结**：`std::stacktrace`（C++23）无需平台相关代码就能捕获和打印调用栈，适合增强异常日志和崩溃报告；使用时注意链接要求、性能开销和调试信息的可用性。

## 本章小结

本章我们学习了标准库诊断设施的核心内容：

1. **`assert`**：开发期的断言，检查“绝不可能发生”的条件，定义 `NDEBUG` 后自动移除，release 零开销；
2. **`errno`**：C 遗留的全局错误码，和 C API 互操作时才用，现代 C++ 优先 `error_code`；
3. **`std::error_code` / `std::error_condition`**：类型安全的系统错误表示，包含错误值、类别和可读信息，可用 `if (ec)` 判断；
4. **标准异常层次**：`std::exception` → `logic_error`/`runtime_error` 等，`what()` 提供错误描述，`catch` 按类型匹配并建议捕获引用；
5. **`noexcept`**：函数承诺不抛异常，有助于编译器优化和容器移动，但违反承诺会导致 `std::terminate`；
6. **异常安全等级**：基本安全（不泄漏、不崩溃）是底线，强安全（回滚到调用前）是理想目标；
7. **`std::stacktrace`（C++23）**：跨平台捕获和打印调用栈，适合异常日志和崩溃报告，注意链接要求和性能开销。

选型口诀：**内部不可能发生用 `assert`；可预见系统错误用 `error_code`；真正异常用 `throw`/`catch`；函数不抛异常标 `noexcept`；想知道是怎么跑到这里的用 `stacktrace`。**

下一章（第 15 章）我们进入内存管理库，学习 `new`/`delete`、`std::allocator`、多态分配器 `std::pmr` 以及未初始化内存算法。

## 练习

1. 写一个函数，用 `assert` 检查传入的指针不为空，再在 `main` 中分别传入合法指针和空指针，观察 `assert` 失败时的输出；然后加上 `-DNDEBUG` 再次编译，观察断言是否被移除。
2. 用 `std::ifstream` 打开一个不存在的文件，捕获流的错误状态，转成 `std::error_code` 并打印 `value()`、`category().name()`、`message()`。
3. 自定义一个继承自 `std::runtime_error` 的异常类，在函数里抛出，在 `main` 中用 `catch (const std::exception& e)` 捕获并打印 `e.what()`。
4. 写一个标记了 `noexcept` 的函数，函数内部不抛异常；再写一个标记 `noexcept` 但内部会抛异常的函数，运行观察程序是否调用 `std::terminate`。
5. 若你的编译器支持 C++23 和 `std::stacktrace`，写一个三层函数调用，在最内层抛出异常，在最外层 `catch` 时打印 `std::stacktrace::current()`，观察调用栈是否包含三层。
