# 第 30 章 测试、诊断与静态分析

代码写出来之后，如何确保它正确、可靠、易维护？本章是第五篇的第二节，覆盖测试、诊断与静态分析三个工程实践维度：

- 30.1 单元测试框架选型与结构化测试：GoogleTest、Catch2、Boost.Test 的定位，以及用现代 C++ 特性编写可读测试；
- 30.2 Sanitizer、静态分析与 `std::stacktrace` 的配合：AddressSanitizer、UndefinedBehaviorSanitizer、ThreadSanitizer 的使用场景，以及用 `stacktrace` 增强崩溃报告。

> **工具约定**：第 7 章起，示例默认采用 CMake + vcpkg 工程模板。Sanitizer 需要编译器支持（GCC/Clang 成熟，MSVC 支持较新）；`std::stacktrace` 是 C++23 特性，部分链接环境需额外库（如 `-lstdc++exp`）。测试框架可通过 vcpkg 引入（`googletest`、`catch2`、`boost-test`）。

## 30.1 单元测试框架选型与结构化测试

### 30.1.1 三大测试框架的定位

C++ 生态中最常用的三个单元测试框架是 GoogleTest、Catch2、Boost.Test。它们都能完成基本的断言和测试用例组织，但设计风格和适用场景有所不同。

| 框架 | 头文件/编译模式 | 断言风格 | 特点 | 适用场景 |
|---|---|---|---|---|
| GoogleTest | 主要 compiled（也有源码集成） | `EXPECT_*` / `ASSERT_*` | 功能最全，mock 支持（gMock），社区生态最丰富 | 通用项目，尤其需要 mock 的场景 |
| Catch2 | 主要 header-only，单头文件版本方便集成 | `REQUIRE` / `CHECK` | 语法简洁，BDD 风格（GIVEN/WHEN/THEN），编译快 | 现代 C++ 项目，快速集成 |
| Boost.Test | 支持 header-only 和 compiled | `BOOST_TEST` / `BOOST_REQUIRE` | 与 Boost 库集成紧密，历史悠久 | 已大量使用 Boost 的项目 |

定位：**纯 Boost 独有**（Boost.Test）；GoogleTest 和 Catch2 是第三方框架，标准库不提供单元测试框架。

### 30.1.2 GoogleTest 基本用法

GoogleTest（gtest）是目前最流行的 C++ 测试框架之一，配合 gMock 还可以做 mock 测试。

```cpp
// gtest_basic.cpp
// 需要链接 gtest 和 gtest_main（或使用 vcpkg 引入 googletest）
#include <gtest/gtest.h>

int add(int a, int b) {
    return a + b;
}

TEST(MathTest, Addition) {
    EXPECT_EQ(add(2, 3), 5);
    EXPECT_NE(add(2, 3), 6);
}

TEST(MathTest, Subtraction) {
    ASSERT_EQ(add(5, -3), 2);   // ASSERT 失败会终止当前测试用例
}

int main(int argc, char** argv) {
    ::testing::InitGoogleTest(&argc, argv);
    return RUN_ALL_TESTS();
}
```

CMake 集成示例：

```cmake
find_package(GTest REQUIRED)

add_executable(math_test test_math.cpp)
target_link_libraries(math_test PRIVATE GTest::gtest_main GTest::gtest)

include(GoogleTest)
gtest_discover_tests(math_test)   # 自动发现并注册测试
```

常用断言：
- `EXPECT_EQ(a, b)` / `ASSERT_EQ(a, b)`：相等断言（EXPECT 失败继续，ASSERT 失败终止当前用例）；
- `EXPECT_TRUE(cond)` / `EXPECT_FALSE(cond)`：布尔断言；
- `EXPECT_THROW(stmt, exception_type)`：期望抛出异常；
- `EXPECT_NO_THROW(stmt)`：期望不抛异常；
- `EXPECT_FLOAT_EQ(a, b)` / `EXPECT_DOUBLE_EQ(a, b)`：浮点数近似相等；
- `EXPECT_DEATH(stmt, regex)`：期望程序崩溃。

### 30.1.3 Catch2 基本用法

Catch2 是 header-only 的现代测试框架，支持 BDD 风格（GIVEN/WHEN/THEN），语法简洁，适合快速集成。

```cpp
// catch2_basic.cpp
// 需要链接或源码集成 Catch2（vcpkg: catch2）
#define CATCH_CONFIG_MAIN   // 自动生成 main 函数
#include <catch2/catch_test_macros.hpp>

int add(int a, int b) {
    return a + b;
}

TEST_CASE("addition works", "[math]") {
    REQUIRE(add(2, 3) == 5);
    REQUIRE(add(-1, 1) == 0);
}

TEST_CASE("string operations", "[string]") {
    std::string s = "hello";
    REQUIRE(s.size() == 5);
    REQUIRE_FALSE(s.empty());
}
```

Catch2 的 `REQUIRE` 失败会终止当前断言，`CHECK` 失败会继续执行后续断言。测试用例可以用标签（`[math]`、`[string]`）分类，运行时按标签筛选。

### 30.1.4 Boost.Test 基本用法

Boost.Test（见第 28.1 节）与 Boost 库集成紧密，断言宏风格独特：

```cpp
// boost_test_basic.cpp
#define BOOST_TEST_MODULE MyTest
#include <boost/test/unit_test.hpp>

BOOST_AUTO_TEST_CASE(test_addition) {
    BOOST_TEST(add(2, 3) == 5);
    BOOST_REQUIRE(add(2, 3) != 6);   // 失败终止当前用例
}
```

### 30.1.5 用现代 C++ 特性编写可读测试

无论选哪个框架，编写可读、可维护的测试代码比框架本身更重要。现代 C++ 特性可以帮助测试代码更简洁、更结构化：

1. **结构化绑定（C++17）**：解构 `std::pair`/`std::tuple` 返回值，断言更清晰；
2. **`std::optional` / `std::expected`**：测试函数返回“值或错误”时，断言更直观；
3. **`constexpr` 测试**：把简单逻辑放在 `static_assert` 中，在编译期就验证，零运行期开销；
4. **参数化测试**：同一逻辑用多组输入验证，避免重复写测试用例。

```cpp
// modern_test_style.cpp
// 需要 GoogleTest，并启用参数化测试支持
#include <gtest/gtest.h>
#include <string>
#include <optional>

std::optional<int> find_first_even(const std::vector<int>& v) {
    for (int x : v) {
        if (x % 2 == 0) return x;
    }
    return std::nullopt;
}

TEST(FindFirstEvenTest, FindsEven) {
    auto result = find_first_even({1, 3, 4, 5, 6});
    ASSERT_TRUE(result.has_value());
    EXPECT_EQ(*result, 4);
}

TEST(FindFirstEvenTest, NotFound) {
    auto result = find_first_even({1, 3, 5});
    EXPECT_FALSE(result.has_value());
}

// 参数化测试：多组输入验证同一逻辑
class AddTest : public ::testing::TestWithParam<std::tuple<int, int, int>> {};
TEST_P(AddTest, HandlesVariousInputs) {
    auto [a, b, expected] = GetParam();   // C++17 结构化绑定
    EXPECT_EQ(add(a, b), expected);
}

INSTANTIATE_TEST_SUITE_P(
    VariousInputs,
    AddTest,
    ::testing::Values(
        std::make_tuple(1, 2, 3),
        std::make_tuple(-1, 1, 0),
        std::make_tuple(0, 0, 0)
    )
);

// constexpr 测试：编译期验证
constexpr int square(int x) { return x * x; }
static_assert(square(5) == 25, "square(5) should be 25");
```

### 30.1.6 测试框架选型建议

| 需求 | 推荐 | 原因 |
|---|---|---|
| 通用项目，需要 mock | GoogleTest | 功能最全，gMock 支持 mock，社区资源多 |
| 快速集成，偏好 header-only | Catch2 | 单头文件版本，语法简洁，编译快 |
| 已大量使用 Boost | Boost.Test | 与 Boost 风格一致，集成成本低 |
| 测试需要按标签筛选 | Catch2 | 标签机制成熟 |

> **小结**：三大框架各有优势，选型取决于项目已有栈和团队偏好。无论用哪个，都应写结构化、可读的测试：使用结构化绑定解构返回值，用 `std::optional`/`std::expected` 表达“值或错误”，用 `static_assert` 做编译期验证，用参数化测试覆盖多组输入。

## 30.2 Sanitizer、静态分析与 `std::stacktrace` 的配合

### 30.2.1 Sanitizer：运行期错误检测

Sanitizer 是编译器插桩工具，在程序运行期检测内存错误、未定义行为、线程竞争等问题。GCC 和 Clang 支持较成熟，MSVC 对 Sanitizer 支持较新版本也在改善。

| Sanitizer | 编译选项 | 检测内容 |
|---|---|---|
| AddressSanitizer (ASan) | `-fsanitize=address` | 堆/栈缓冲区溢出、使用后释放（use-after-free）、双重释放、内存泄漏 |
| UndefinedBehaviorSanitizer (UBSan) | `-fsanitize=undefined` | 空指针解引用、整数溢出、对齐问题、未初始化读取 |
| ThreadSanitizer (TSan) | `-fsanitize=thread` | 数据竞争、死锁风险 |
| MemorySanitizer (MSan) | `-fsanitize=memory` | 未初始化内存读取（Clang） |

使用示例：

```bash
# 编译时开启 ASan + UBSan
g++ -std=c++20 -g -O1 -fsanitize=address,undefined my_program.cpp -o my_program

# 运行，若出错 Sanitizer 会打印详细报告并终止
./my_program
```

**注意**：Sanitizer 会显著降低运行速度并增加内存占用，适合在测试环境和 CI 中使用，生产环境通常不开启。

### 30.2.2 静态分析：clang-tidy 与 CMake 集成

静态分析在不运行程序的情况下检查源代码，发现潜在缺陷、代码异味和风格问题。`clang-tidy` 是最常用的 C++ 静态分析工具之一。

CMake 可以导出编译命令数据库（`compile_commands.json`），供 `clang-tidy` 使用：

```cmake
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)   # 生成 compile_commands.json
```

然后在项目根目录运行：

```bash
clang-tidy -p build src/*.cpp -- -std=c++20
```

常用检查组（checks）：
- `clang-analyzer-*`：静态分析器，如空指针解引用、内存泄漏；
- `bugprone-*`：容易出 bug 的模式，如移动后使用、裸 new/delete；
- `performance-*`：性能建议，如不必要的拷贝；
- `modernize-*`：现代化建议，如用 `nullptr` 代替 `NULL`、用 `auto` 简化类型。

### 30.2.3 `std::stacktrace` 增强崩溃报告

第 14.3 节已经介绍了 `std::stacktrace`（C++23）：无需平台相关代码就能捕获和打印调用栈。在测试和诊断场景中，它可以配合 Sanitizer 和异常处理，让崩溃报告更有用。

```cpp
// stacktrace_with_sanitizer.cpp
// 需要 C++23，GCC/Clang 通常需链接 -lstdc++exp
#include <iostream>
#include <stacktrace>
#include <stdexcept>
#include <vector>

void deep_function(std::vector<int>& v) {
    // 故意越界访问，ASan 会捕获
    std::cout << v.at(100) << '\n';   // 或者 v[100] 配合 ASan
}

void middle_function() {
    std::vector<int> v = {1, 2, 3};
    deep_function(v);
}

int main() {
    try {
        middle_function();
    } catch (const std::exception& e) {
        std::cerr << "异常：" << e.what() << '\n';
        std::cerr << "调用栈：\n" << std::stacktrace::current() << '\n';
    }
}
```

如果开启了 AddressSanitizer，`v.at(100)` 抛出 `std::out_of_range` 时，`std::stacktrace::current()` 可以打印出从 `main` 到 `deep_function` 的完整调用链，帮助快速定位问题是在哪个调用层引入的越界索引。

### 30.2.4 三者的配合使用

| 工具 | 作用 | 使用阶段 |
|---|---|---|
| 单元测试框架 | 验证功能正确性 | 每次构建、每次提交 |
| Sanitizer | 检测运行期内存和未定义行为 | 测试环境、CI |
| 静态分析 (clang-tidy) | 静态发现缺陷和代码异味 | 代码提交前、CI |
| `std::stacktrace` | 崩溃/异常时打印调用栈 | 生产崩溃报告、测试失败诊断 |

理想的工程流程是：开发时编写单元测试并运行；提交代码前跑 clang-tidy；CI 中用 Sanitizer 构建并运行测试；生产环境若发生崩溃，通过 `std::stacktrace` 增强的崩溃报告定位问题。

## 本章小结

本章我们学习了测试、诊断与静态分析的工程实践：

1. **单元测试框架**：GoogleTest（功能全、有 gMock）、Catch2（header-only、语法简洁）、Boost.Test（与 Boost 集成）；选型取决于项目栈和团队偏好；
2. **结构化测试**：用结构化绑定解构返回值，用 `std::optional`/`std::expected` 表达“值或错误”，用 `static_assert` 做编译期验证，用参数化测试覆盖多组输入；
3. **Sanitizer**：ASan 检测内存错误，UBSan 检测未定义行为，TSan 检测线程竞争，适合测试环境和 CI；
4. **静态分析**：clang-tidy 配合 `CMAKE_EXPORT_COMPILE_COMMANDS ON`，静态发现缺陷和代码异味；
5. **`std::stacktrace`**：C++23 捕获调用栈，配合异常处理和 Sanitizer 增强崩溃报告，快速定位问题。

选型口诀：**测试框架按团队偏好选（GoogleTest/Catch2/Boost.Test）；可读测试用结构化绑定和参数化；CI 中开 Sanitizer；提交前跑 clang-tidy；崩溃报告加 `stacktrace`。**

## 练习

1. 用 GoogleTest 写一个参数化测试，验证一个“计算阶乘”函数在多个输入下的输出。
2. 用 `static_assert` 和 `constexpr` 函数在编译期验证一个数学恒等式（如第 n 个斐波那契数）。
3. 用 `g++ -fsanitize=address,undefined` 编译一个故意有“使用后释放”bug 的程序，运行观察 Sanitizer 报告。
4. 在 CMake 项目里开启 `CMAKE_EXPORT_COMPILE_COMMANDS ON`，用 `clang-tidy` 检查源代码，修复一个 `bugprone-*` 类型的警告。
5. 用 `std::stacktrace::current()` 在一个抛出异常的函数调用链中打印调用栈，验证是否包含多层调用。
